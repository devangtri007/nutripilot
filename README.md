# NutriPilot — Strengthened Phase 4

Phase 4 now uses a **recipe-first data layer** instead of asking the LLM to invent ingredient combinations.

## What's new

- Expanded `data/foods.csv` to a substantially larger starter catalogue.
- Added `data/recipes.csv` with 45 real meal/recipe combinations spanning breakfast, lunch, dinner and snacks.
- Recipes include:
  - meal type
  - cuisine
  - broad region
  - season
  - diet compatibility
  - goal tags
  - weather tags
  - fixed ingredient quantities
- AI selects `recipe_id` values from the catalogue.
- The app rejects unsupported recipe IDs.
- Nutrition is calculated deterministically from `foods.csv`, not generated by the AI.
- Candidate recipes are filtered by diet, restrictions, season and location relevance before being sent to the model.
- A fallback pool prevents the catalogue from becoming too narrow when seasonal filtering removes too many options.

## Data provenance

The food values in this prototype are a curated starter dataset and should not be treated as clinical nutrition data.

For a production-grade data layer, replace/augment these values with properly licensed authoritative datasets. USDA FoodData Central provides downloadable/API-accessible nutrient data and publishes its data under CC0; see:
https://fdc.nal.usda.gov/api-guide/
https://fdc.nal.usda.gov/download-datasets/

For India-specific composition data, ICMR-NIN's Indian Food Composition Tables (IFCT 2017) cover 528 key foods and 151 nutrient components. Review NIN's permissions before embedding the source data into a distributed product:
https://www.nin.res.in/ebooks/IFCT2017.pdf

## Setup

Create `.streamlit/secrets.toml`:

```toml
OPENAI_API_KEY = "your-api-key"
```

Do not commit API keys.

Run:

```bash
pip install -r requirements.txt
streamlit run streamlit_app.py
```

## Architecture

Location selector
→ Open-Meteo geocoding
→ current weather + season
→ profile + context filters
→ recipe candidate catalogue
→ LLM ranks/selects recipes
→ recipe ID validation
→ deterministic nutrition calculation
→ meal plan UI

## Important prototype limitations

- Food nutrition values are approximate starter values.
- The location catalogue is curated rather than exhaustive.
- Allergy matching is simple text matching and is not suitable for medical-grade allergen verification.
- Recipes are fixed combinations, not personalized portions.
- The app is for meal-planning exploration, not medical or dietary advice.


## Phase 5 — Conversational Refinement

Phase 5 adds a conversational refinement layer after the initial plan is generated.

Example requests:
- "Make dinner higher protein"
- "No rice in the plan"
- "Keep meals under 20 minutes"
- "Replace lunch with something quicker"

The LLM does not directly rewrite ingredients. It selects replacement `recipe_id`
values from the existing candidate catalogue. The application then validates each
recipe and recalculates nutrition deterministically.

Recipe metadata now includes:
- `prep_time_min`
- `cook_time_min`
- `total_time_min`
- `difficulty`

This enables explicit constraints such as a maximum total cooking time.

### Phase 5 architecture

Initial plan:
`Profile + location/weather → filtered recipes → AI selection → validation → nutrition`

Refinement:
`User message → AI interprets constraint → recipe IDs from catalogue → validation → deterministic nutrition → updated plan`

### Current limitation

The conversation layer can only satisfy requests that can be represented by the
current recipe catalogue and metadata. It intentionally does not invent new recipes.
This is a deliberate product/safety design choice for the prototype.
